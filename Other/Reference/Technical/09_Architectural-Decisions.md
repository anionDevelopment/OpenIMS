# 9. Architectural Decisions

## Decision-board

| Decision-identifier | Date | Decision | Reason and notes |
| ------------------- | ---- | -------- | ---------------- |
| D001 | 2026-09-21 | OpenIMS should be hostable on premises. | Base requirement for many user. |
| D002 | 2026-09-21 | C# for backend | Appropriate for usecase. |
| D003 | 2026-09-21 | Angular for web-frontend | Appropriate for usecase. |
| D004 | 2026-09-21 | Support for MariaDB as database | Reasons:<br>- Open source.<br>- Free for private user. |
| D005 | 2026-09-21 | Support for PostgreSQL as database | Reasons:<br>- MariaDB is not stable enough on all systems.<br>- MariaDB does still not support transactional DDL-operations, which makes a failed migration hard to recover from. |
| D006 | 2026-09-21 | No dedicated codeunit for an app-client | The web-frontend-client is supposed to be usable also on mobile devices. If there are more requirements which justify the effort then an app-client can still be developed. |
| D007 | 2026-09-21 | Timestamps will be stored in UTC in the persistence | Storing timezones in the database is tricky. To have a consistent way of storing timestamp-values correctly, timestamps are converted to UTC and the application which displays the value converts it back to the local timezone of the user. |
| D008 | 2026-09-21 | Authentication by username/password with an access-token | The simplest mechanism which covers the requirement. An external identity-provider can be added later without changing the endpoints which the frontend uses, because the frontend only ever sees the access-token. |
| D009 | 2026-09-21 | The database-schema is defined by explicit migration-scripts and not by an object-relational mapper | The schema stays readable and reviewable, and the difference between two supported database-types stays a difference between two folders of scripts instead of a difference in the business-logic. |
| D010 | 2026-10-08 | The inventory is modeled as a strict hierarchy location → building → container → item using the composite-pattern | The model represents the physical world, where a thing is in exactly one place and nothing is in itself. The composite-pattern allows nesting containers to any depth with one uniform interface (`IContainer`/`IContainee`). |
| D011 | 2026-10-08 | An item has a target place (its container) and a real place (`IRealPlace`) | Where an item belongs to and where it actually is differ in practice. `IRealPlace` is an own interface so that further kinds of real places which are no containers can be added later. |
| D012 | 2026-10-08 | The rules of the inventory-hierarchy are checked in the business-logic and not in the persistence | The rules exist exactly once and apply the same way to all persistences (including the transient one). The persistence only ensures what its structure ensures anyway (exactly one parent, referenced objects exist). |
| D013 | 2026-10-08 | All inventory-objects are stored in one table `InventoryObjects` with a reference to the parent | A container can be contained in a building or in a container. One table allows a real foreign-key for the parent and for the real place, which would not be possible with one table per type. |
| D014 | 2026-10-08 | Between building and container there is the type `Area`, which can also be directly in a location | A thing is kept in a room of a building or in an area outside of a building (for example a yard or a terrace). "Area" fits both, "room" would not fit a yard. A building is no container anymore: everything in it is in one of its areas. This refines D010. |
| D015 | 2026-10-08 | A group which gets access to inventory-objects is a role of the GRYLibrary | The GRYLibrary has no separate group-type; its authorization already treats roles as groups (attribute `Authorize`). So there is one concept for the permissions of a user and for the access to inventory-objects. |
| D016 | 2026-10-08 | Only the direct assignments of groups to authorizable items are stored; the access to everything which is contained is computed at runtime | The inherited access always follows the current hierarchy (also after a move) without having to update stored data, and there is no redundant data which could become inconsistent. |
| D017 | 2026-10-08 | An inventory-object is selected by a dropdown with an inline-search which is executed in SQL and returns a limited amount of id-label-pairs | The inventory can be large, so loading all objects for a selection would be slow. The search in SQL only transfers what is displayed. The dropdown is one reusable component, because the selection of an inventory-object is needed on several pages. |
| D018 | 2026-10-08 | The name of a group is passed as query-parameter and not as header | A header can only reliably transport ASCII-characters, but the name of a group can contain any character (for example an umlaut). |
