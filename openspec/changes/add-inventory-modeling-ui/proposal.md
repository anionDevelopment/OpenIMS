# Proposal

## Why

The backend already implements the inventory-hierarchy (location → building → area → container → item) in its business-logic, but there is neither an endpoint nor a user-interface for it, so the inventory can not be modeled at all by a user. A user has to be able to create locations, add buildings to them and define the areas (rooms) and containers (boxes) inside, so that the physical world can be represented in OpenIMS.

## What Changes

- New endpoints in `OpenIMSBackendController` which make the existing business-logic for the inventory available via http:
  - read the complete inventory as a tree
  - create a location, a building, an area, a container and an item
  - change name and description of an inventory-object
  - delete an inventory-object
- Every logged-in user (role `Users`) can use these endpoints; no administrator-privileges are required.
- Every logged-in user sees and changes the complete inventory. The read-access which groups grant (spec `inventory-access`) is **not** applied to these endpoints, because it is not specified yet which operation requires which access. This is a deliberate decision of the product-owner for this change and has to be revisited when access-checks of inventory-operations are specified.
- New page "Inventory" in the user-area of the frontend (`user/inventory`, menu-entry in the user-menu) which displays the inventory as an expandable tree. Every node offers the actions which the hierarchy allows for its type (add building/area/container/item, edit, delete); a dialog asks for name and description.
- A new item is created with its target place as its real place. Moving objects and changing the real place of an item are not part of this change.
- Visual-regression-testcase for the new page.

## Capabilities

### New Capabilities

- `inventory-modeling`: Modeling the inventory via the web-api and the web-ui: reading the inventory-tree, creating, editing and deleting inventory-objects, who may do it, and how the page "Inventory" behaves.

### Modified Capabilities

None. The rules of the hierarchy (`inventory-hierarchy`) are reused unchanged; the endpoints only expose them. `inventory-access` stays unchanged as well: it defines how the access is computed, and this change does not apply it to the new endpoints (see above).

## Impact

- Backend: `Controller/OpenIMSBackendController.cs` (new endpoints), new DTOs in `Model/DTOs`, mapping of the business-types to a tree-DTO, testcases of the business-logic and of the mapping.
- API-specification: new routes under `/API/v0/OpenIMSBackend/...`; the generated frontend-client (`src/app/generated/open-ims-backend`) is regenerated.
- Frontend: new component in `modules/user-area`, new route in `app.routes.ts`, menu-entry in `user-area-container`, new texts (translations are generated by the task `Translate`).
- Visual-regression: new testcase in `OpenIMSFrontend/e2e`, new baselines for chromium, firefox and webkit.
- Documentation: `ReadMe.md` (features), `Other/Reference/Reference.md` (feature-table), changelog.
